## Overview

Avenor uses **PostgreSQL** as its database, accessed exclusively through **Prisma ORM**. This document covers schema design principles, access patterns, and conventions. The Prisma schema lives at `prisma/schema.prisma` and is the canonical database definition.

## Core Principles

### 1. Prisma Is the Source of Truth

The Prisma schema file is the single source of truth for the database structure. Database changes made outside of Prisma migrations are forbidden. No direct `ALTER TABLE` commands in production.

### 2. Repository Pattern

No business logic code imports Prisma directly. All database access goes through repository functions in `src/modules/[domain]/repository.ts`. This isolates the database layer and makes testing easier.

```ts
// ✅ Service calls repository
// src/modules/applications/service.ts
import { applicationRepository } from './repository'
const application = await applicationRepository.findById(id)

// ❌ Service calls Prisma directly
import { db } from '@/lib/db'
const application = await db.jobApplication.findUnique({ where: { id } })
```

### 3. Single Client Instance

The Prisma client is a singleton defined in `src/lib/db.ts`. Never instantiate `new PrismaClient()` anywhere else.

### 4. Never Raw SQL (Without ADR)

Raw SQL queries are forbidden unless explicitly approved by an Architecture Decision Record. Prisma provides sufficient query capability for all expected use cases.

## Data Model Rules

### Primary Keys

All primary keys are **UUIDs** generated by Prisma:

```prisma
model JobApplication {
  id String @id @default(cuid())
  ...
}
```

CUID (Collision-resistant Unique IDentifier) is preferred over UUID for:
- Better performance in sorted indexes
- URL-safe by default
- Shorter than UUID

### Timestamps

Every table must have `createdAt` and `updatedAt`:

```prisma
model JobApplication {
  id        String   @id @default(cuid())
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")
  ...
}
```

### Soft Deletes

Records that have referential integrity (e.g., applications that have interviews) use soft delete:

```prisma
model JobApplication {
  ...
  deletedAt DateTime? @map("deleted_at")
}
```

All queries against soft-deleted tables must include `WHERE deleted_at IS NULL` (Prisma middleware handles this automatically).

### User Ownership

Every user-owned record must include a `userId` foreign key:

```prisma
model JobApplication {
  id     String @id @default(cuid())
  userId String @map("user_id")
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  ...
}
```

`onDelete: Cascade` ensures that deleting a user removes all their data.

## Prisma Schema Conventions

```prisma
// ✅ Model names: PascalCase singular
model JobApplication { ... }
model InterviewSession { ... }

// ✅ Field names: camelCase in Prisma, mapped to snake_case in DB
companyName String @map("company_name")
appliedAt   DateTime? @map("applied_at")

// ✅ Enum names: PascalCase
enum ApplicationStatus {
  APPLIED
  INTERVIEWING
  OFFERED
  REJECTED
  WITHDRAWN
  ACCEPTED
}

// ✅ Table names: snake_case plural (via @@map)
model JobApplication {
  @@map("job_applications")
}
```

## Indexing Policy

Indexes are required for:
1. Every foreign key column
2. Any column used in `WHERE` clauses for frequently-run queries
3. Any column used for `ORDER BY` on paginated queries
4. Composite indexes for compound filters

```prisma
model JobApplication {
  @@index([userId])                           // FK index
  @@index([status])                           // Status filter
  @@index([userId, status])                   // Compound — filtered list
  @@index([userId, appliedAt(sort: Desc)])    // Sorted paginated list
}
```

## Migration Workflow

1. **Edit `prisma/schema.prisma`**
2. **Generate migration:** `pnpm prisma migrate dev --name describe-change`
3. **Review** the generated SQL in `prisma/migrations/`
4. **Apply** automatically during `migrate dev`
5. **Commit** both `schema.prisma` and the migration files

Migration files are **never hand-edited** after creation. If a migration needs adjustment, roll it back and regenerate.

Full migration guide → [`migrations.md`](./migrations.md)

## Query Performance Rules

- Every query that returns a list must be paginated — no unbounded `findMany()`
- Avoid N+1 queries — use Prisma `include` or `select` with relations
- Log slow queries (>500ms) at `warn` level
- Use database-level aggregations (`count`, `sum`, `avg`) instead of fetching all records and aggregating in JavaScript
