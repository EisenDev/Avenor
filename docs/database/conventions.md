## Naming Reference Table

| Item | Convention | Example |
|---|---|---|
| Table names | `snake_case`, plural | `job_applications` |
| Column names | `snake_case` | `company_name`, `applied_at` |
| Primary key | Always `id` | `id UUID` |
| Foreign keys | `[table_singular]_id` | `user_id`, `application_id` |
| Boolean columns | `is_` or `has_` prefix | `is_active`, `has_offer` |
| Timestamp columns | verb + `_at` | `applied_at`, `created_at`, `deleted_at` |
| Count columns | noun + `_count` | `interview_count` |
| Enum type names | `snake_case` + `_type` or `_status` | `application_status` |
| Index names | `[table]_[columns]_idx` | `job_applications_user_id_idx` |
| Unique constraints | `[table]_[columns]_unique` | `users_email_unique` |

## Standard Column Set

Every table that stores user data includes these columns:

```sql
id          TEXT        PRIMARY KEY     -- CUID generated by Prisma
user_id     TEXT        NOT NULL        -- Owner reference (FK to users.id)
created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at  TIMESTAMPTZ NOT NULL        -- Managed by Prisma @updatedAt
deleted_at  TIMESTAMPTZ                 -- NULL = active, set = soft-deleted
```

## Relationship Conventions

### One-to-Many

```prisma
// The "many" side holds the foreign key
model Interview {
  applicationId String        @map("application_id")
  application   JobApplication @relation(fields: [applicationId], references: [id])
}
```

### Many-to-Many (via join table)

```prisma
// Explicit join table (not implicit Prisma m-n)
model ApplicationTag {
  applicationId String @map("application_id")
  tagId         String @map("tag_id")

  application JobApplication @relation(fields: [applicationId], references: [id])
  tag         Tag            @relation(fields: [tagId], references: [id])

  @@id([applicationId, tagId])
  @@map("application_tags")
}
```

Always use explicit join tables (not Prisma's implicit `@relation` many-to-many). Explicit join tables allow adding metadata to the relationship.

### Cascade Delete Rules

| Relationship | Rule | Reason |
|---|---|---|
| User → all owned records | `CASCADE` | Deleting account removes all data |
| Application → interviews | `CASCADE` | Interview can't exist without application |
| Application → documents | `RESTRICT` | Documents might be reusable (warn before delete) |
| Application → emails | `SET NULL` | Email thread exists independently |

## JSON/JSONB Usage

Use JSONB columns only for:
- AI metadata (prompt, response, token counts)
- Flexible attributes that genuinely vary per record
- Integration configuration blobs

Never use JSONB to avoid designing a proper schema. If you're storing structured data that you'll query, it belongs in proper columns.

```prisma
model AiRequest {
  // ✅ JSONB for AI metadata — structure varies by operation type
  promptData    Json @map("prompt_data")
  responseData  Json @map("response_data")
}

model JobApplication {
  // ❌ Never use JSONB to avoid proper modeling
  interviewDates Json  // Wrong — InterviewSession table should exist
}
```

## Schema Design Review Checklist

Before merging any schema change:

- [ ] All new tables follow naming conventions
- [ ] Every new table has `id`, `created_at`, `updated_at`
- [ ] Foreign keys have cascade rules defined
- [ ] All frequently-queried columns have indexes
- [ ] Enum values are in `SCREAMING_SNAKE_CASE`
- [ ] Boolean columns start with `is_` or `has_`
- [ ] JSONB only used where structure genuinely varies
- [ ] Migration is reviewed and safe to run zero-downtime
